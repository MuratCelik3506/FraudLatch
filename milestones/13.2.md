# Milestone 13.2 — Load Testing

Status: Deferred
Parent: 13
Depends on: 10.3
Owner: Repository maintainer

## Goal

Measure controlled ingestion and processing throughput using the existing API/replay contracts.

## Why this matters

Load testing quantifies bottlenecks and validates queue/backlog metrics without claiming production capacity from a development laptop.

## Scope

- k6 or Locust test harness
- 100 and 500 request-per-second scenarios
- API latency/error rate
- Worker throughput and queue backlog
- Reproducible test environment

## Out of scope

- Production-scale capacity claims
- Cloud load generation by default
- Autoscaling

## Expected changes

Add load-test scripts, scenario documentation, and result artifact format.

## Implementation checklist

- [ ] Define payload generation and collision policy.
- [ ] Run baseline at 100 req/s.
- [ ] Run stress scenario at 500 req/s where local resources permit.
- [ ] Capture p50/p95/p99 latency and error rate.
- [ ] Capture worker throughput, backlog, and DLQ count.
- [ ] Record host/resource context with every result.

## Interfaces and contracts

Load tests use the public ingestion API and never bypass the outbox/queue path.

## Validation

Run the same scenario twice and compare result format and major signals.

## Acceptance criteria

- [ ] Results are reproducible enough to compare commits.
- [ ] Backlog and failure behavior are visible.
- [ ] No production capacity claim is made from local measurements.

## Failure and edge cases

Resource exhaustion, client timeout, partial replay, and increasing DLQ must stop the test or mark it failed rather than being reported as throughput success.

## Definition of done

A documented, repeatable local load baseline exists.

## Follow-up

Use queue depth signals for 13.3 only after AWS deployment.

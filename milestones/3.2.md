# Milestone 3.2 — Outbox Dispatcher

Status: Not started
Parent: 3
Depends on: 3.1, 4.2
Owner: Repository maintainer

## Goal

Move pending outbox events into the queue using a dedicated, restartable process.

## Why this matters

Separating publication from the API keeps ingestion fast and makes queue outages recoverable. A separate process also gives publication backlog and failure states their own operational signals.

## Scope

- Dispatcher process and graceful shutdown
- Batch polling every second
- `FOR UPDATE SKIP LOCKED`
- Queue publish integration
- Published/failed state transitions
- Outbox backlog metrics

## Out of scope

- Risk scoring
- SQS deployment
- Manual admin UI

## Expected changes

Add dispatcher entrypoint, outbox polling service, queue-port dependency, and dispatcher tests.

## Implementation checklist

- [ ] Poll pending rows in batches of 100.
- [ ] Claim rows with row-level locking.
- [ ] Publish the exact stored event envelope.
- [ ] Mark successful rows published with timestamp.
- [ ] Record failure, attempt count, and next retry time.
- [ ] Stop polling on SIGTERM after the current batch.
- [ ] Emit pending, published, and failure metrics.

## Interfaces and contracts

Dispatcher input is a pending outbox row; output is a queue message and a durable publication state. It must not mutate the transaction record.

## Validation

Test queue outage, dispatcher restart, concurrent dispatcher processes, duplicate publication, and graceful shutdown.

## Acceptance criteria

- [ ] Pending rows eventually publish after a temporary queue outage.
- [ ] Concurrent dispatchers do not process the same row simultaneously.
- [ ] A crash after publish is safe because worker processing is idempotent.
- [ ] Failed rows are retained and observable.

## Failure and edge cases

Do not acknowledge or delete an outbox row before queue publication succeeds. A permanently malformed stored payload must remain visible as failed for manual inspection.

## Definition of done

A standalone dispatcher can be stopped/restarted and still deliver every accepted event at least once.

## Follow-up

Use 4.2’s Redis Streams implementation as the first queue adapter.

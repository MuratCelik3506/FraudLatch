# Milestone 6.2 — Risk Result Persistence

Status: Complete
Parent: 6
Depends on: 2.1, 5.1, 6.1
Owner: Repository maintainer

## Goal

Persist risk decisions and processing history so clients can distinguish pending, completed, and failed work.

## Why this matters

The result API and operational debugging need a durable state, not only a queue acknowledgement or cache entry. Audit records also make retry behavior explainable.

## Scope

- Risk assessment upsert
- Processing event audit rows
- Pending/processing/completed/failed states
- Safe error codes
- Risk query endpoint

## Out of scope

- Grafana dashboard
- ML model metadata
- User-facing case management

## Expected changes

Add result repository/service, worker persistence transaction, query route, and audit tests.

## Implementation checklist

- [x] Upsert one current assessment per transaction.
- [x] Record every attempt in `processing_events`.
- [x] Store reasons and engine version as structured data.
- [x] Store safe error code for terminal failure.
- [x] Return `200`, `202`, or `404` according to risk state.
- [x] Implement `GET /v1/risks/high` with bounded pagination and deterministic ordering.
- [x] Ensure result commit and processing audit are atomic.

## Interfaces and contracts

`GET /v1/transactions/{transaction_id}/risk` returns `200` for completed or failed known transactions, `202` for pending/processing, and `404` for unknown transactions.

## Validation

Test result upsert, repeated event, concurrent worker writes, pending query, completed query, failed query, and unknown transaction.

## Acceptance criteria

- [x] Exactly one current result exists per transaction.
- [x] High-risk queries return only completed HIGH assessments and are paginated.
- [x] Attempt history is queryable.
- [x] Cache misses do not change API correctness.
- [x] Internal stack traces are never returned.

## Failure and edge cases

If result persistence fails, the message remains retryable and unacknowledged. A terminal failure is marked only after the event is safely dead-lettered.

## Definition of done

Worker output, audit history, and risk query states are durable and tested.

## Follow-up

Add end-to-end replay and failure tests in Milestone 10.3.

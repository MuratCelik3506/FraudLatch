# Milestone 4.2 — Redis Streams Adapter

Status: Complete
Parent: 4
Depends on: 4.1
Owner: Repository maintainer

## Goal

Implement the local queue adapter using Redis Streams and consumer groups.

## Why this matters

Redis is already required for velocity state and local infrastructure. Streams provide persistence, consumer ownership, acknowledgements, and pending-entry recovery without introducing another local broker.

## Scope

- Async Redis client factory
- Main stream `fraudlatch:transactions:v1`
- Consumer group management
- Publish/receive/ack
- Pending-entry reclaim
- Adapter contract tests

## Out of scope

- SQS
- Business retry policy; 4.3 defines it.
- Redis cluster/high availability

## Expected changes

Add Redis adapter, connection configuration, stream/group bootstrap, and adapter integration tests.

## Implementation checklist

- [x] Create the stream consumer group idempotently.
- [x] Serialize versioned envelopes as message fields.
- [x] Implement batch receive for a named consumer.
- [x] Acknowledge only by stream message ID.
- [x] Reclaim stale pending entries after worker restart.
- [x] Expose connection and queue health checks.

## Interfaces and contracts

Stream: `fraudlatch:transactions:v1`.

Consumer group: `risk-workers`.

The adapter returns a `QueueMessage` containing the envelope, stream ID, and attempt metadata.

## Validation

Run two consumers, stop one while it owns a message, restart it, and verify the message is reclaimed at least once.

## Acceptance criteria

- [x] Dispatcher can publish a valid envelope.
- [x] Multiple workers consume through one group.
- [x] Acknowledged messages are not returned to the group.
- [x] Unacknowledged messages are recoverable.
- [x] Invalid Redis URLs fail clearly.

## Failure and edge cases

Redis restarts must not cause acknowledged messages to be treated as completed database work unless the worker’s DB state confirms completion.

## Definition of done

Redis Streams passes the queue contract tests and supports dispatcher-to-worker delivery locally.

## Follow-up

Add retry scheduling and DLQ handling in 4.3.

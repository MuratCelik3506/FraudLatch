# Milestone 8.1 — Application Metrics and Structured Logs

Status: Not started
Parent: 8
Depends on: 2, 3, 6
Owner: Repository maintainer

## Goal

Instrument API, dispatcher, worker, and risk processing with low-cardinality Prometheus metrics and structured JSON logs.

## Why this matters

Metrics turn failure scenarios into measurable acceptance criteria. Structured logs connect a queue event to a transaction without exposing sensitive or high-cardinality data as metric labels.

## Scope

- Counters and histograms
- Request/processing latency
- Outbox backlog
- Retry/DLQ count
- JSON logs
- Correlation fields

## Out of scope

- Distributed traces
- PII redaction framework
- CloudWatch exporters

## Expected changes

Add `fraudlatch/observability` helpers, API/worker instrumentation, and metric/log tests.

## Implementation checklist

- [ ] Add received, processed, fraud-detected, failure, retry, DLQ counters.
- [ ] Add processing and queue latency histograms.
- [ ] Add outbox pending gauge.
- [ ] Add `event_id`, `transaction_id`, component, attempt, status, duration, and error code to logs.
- [ ] Keep IDs out of metric labels.
- [ ] Ensure instrumentation errors cannot fail business processing.

## Interfaces and contracts

Metrics include:

```text
fraudlatch_transactions_received_total
fraudlatch_transactions_processed_total
fraudlatch_processing_failures_total
fraudlatch_outbox_pending_total
fraudlatch_dlq_messages_total
```

## Validation

Assert metric increments around successful, duplicate, failed, retried, and DLQ processing.

## Acceptance criteria

- [ ] `/metrics` exposes valid Prometheus text.
- [ ] Logs are parseable JSON.
- [ ] No customer/transaction ID is a metric label.
- [ ] Metrics distinguish API, dispatcher, and worker components.

## Failure and edge cases

Metric backend absence or serialization failure must be logged and ignored without changing API/worker outcomes.

## Definition of done

All critical pipeline transitions are observable with stable metric names and correlation fields.

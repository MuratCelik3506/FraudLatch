# Milestone 4 — Queue Abstraction and Redis Streams

Status: Not started
Parent: —
Depends on: 1.3
Owner: Repository maintainer

## Goal

Define a queue contract independent of infrastructure and implement reliable local delivery with Redis Streams.

## Why this matters

The application must be able to evolve from local Redis Streams to AWS SQS without rewriting dispatcher or worker domain logic. The abstraction also makes retry, acknowledgement, and contract testing explicit.

## Scope

- Versioned Pydantic event envelope
- Queue port and message handle
- Redis connection factory
- Streams and consumer groups
- Pending-entry recovery
- Retry/DLQ behavior

## Out of scope

- AWS SQS adapter; see 12.1.
- Kafka
- Exactly-once delivery claims

## Expected changes

Child milestones 4.1–4.3 define the public interface, Redis implementation, and failure policy.

## Implementation checklist

- [ ] Complete 4.1.
- [ ] Complete 4.2.
- [ ] Complete 4.3.
- [ ] Run adapter contract tests.

## Interfaces and contracts

All adapters provide at-least-once delivery. A consumer acknowledges only after the downstream database transaction commits.

## Validation

Use contract tests that run against the queue port and can later be reused for SQS.

## Acceptance criteria

- [ ] Worker/domain code has no Redis-specific calls.
- [ ] Multiple consumers can share a group.
- [ ] Pending messages survive process restart.
- [ ] Failed messages are retried and dead-lettered.

## Failure and edge cases

Redis restart, duplicate delivery, stale consumer ownership, malformed envelope, and unsupported schema version must have explicit behavior.

## Definition of done

Redis Streams passes queue contract tests and the dispatcher can publish to it.

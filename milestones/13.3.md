# Milestone 13.3 — Worker Autoscaling

Status: Deferred
Parent: 13
Depends on: 12.4
Owner: Repository maintainer

## Goal

Scale ECS worker count from SQS queue depth while preserving bounded cost and idempotent processing.

## Why this matters

Queue-depth scaling demonstrates an operational feedback loop, but it is meaningful only after the AWS worker and alarms are working.

## Scope

- SQS queue-depth metric
- ECS desired-count policy
- Minimum/maximum worker count
- Scale-out/scale-in cooldowns
- Cost guardrails

## Out of scope

- Kubernetes autoscaling
- Unlimited worker growth
- Multi-region scaling

## Expected changes

Add Terraform autoscaling resources and an operational runbook.

## Implementation checklist

- [ ] Define queue-depth target and worker bounds.
- [ ] Add scale-out and scale-in cooldowns.
- [ ] Validate duplicate-safe concurrent processing.
- [ ] Add cost and backlog alarms.
- [ ] Verify scale-in does not interrupt committed work.

## Interfaces and contracts

Autoscaling changes worker count only; message, risk, idempotency, and DLQ contracts remain unchanged.

## Validation

Create controlled backlog, observe scale-out, drain queue, and observe safe scale-in.

## Acceptance criteria

- [ ] Backlog decreases under scale-out.
- [ ] Worker count respects configured bounds.
- [ ] No message loss or duplicate result is introduced.

## Failure and edge cases

Metric delay, alarm failure, throttling, and scale-in during a long processing lease must be observable.

## Definition of done

Queue-depth autoscaling is bounded, measurable, and cost-aware.

## Follow-up

Consider blue/green only after autoscaling is stable.

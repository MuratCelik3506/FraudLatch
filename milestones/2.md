# Milestone 2 — Persistence and API Contract

Status: Not started
Parent: —
Depends on: 1.3
Owner: Repository maintainer

## Goal

Define and implement the first durable transaction boundary: validated API input becomes a PostgreSQL record with explicit idempotency behavior.

## Why this matters

The database record is the foundation for outbox delivery, risk processing, auditability, and query consistency. A precise API contract prevents later queue and worker code from compensating for ambiguous input behavior.

## Scope

- Async SQLAlchemy and Alembic
- Transaction persistence
- API request/response models
- Duplicate and conflict semantics
- Health and readiness boundaries

## Out of scope

- Queue publishing
- Risk scoring
- Authentication
- AWS persistence

## Expected changes

Child milestones 2.1 and 2.2 define schema, migrations, repositories, routes, and contract tests.

## Implementation checklist

- [ ] Complete 2.1.
- [ ] Complete 2.2.
- [ ] Verify API and database contracts together.

## Interfaces and contracts

New transactions return `202 Accepted`; identical retries return `202 Accepted`; conflicting payloads with the same ID return `409 Conflict`; invalid payloads return `422 Unprocessable Entity`.

## Validation

Run migration tests and API contract tests from child milestones.

## Acceptance criteria

- [ ] Valid transactions persist with UTC timestamps.
- [ ] Duplicate behavior is deterministic and database-backed.
- [ ] API does not synchronously calculate risk.

## Failure and edge cases

Database unavailability must produce a clear dependency error and must never return success for an uncommitted transaction.

## Definition of done

Child milestones 2.1 and 2.2 pass and the API can accept/query a transaction without any queue or worker implementation.

## Follow-up

Use the transaction boundary as the insertion point for Milestone 3’s outbox.

# Milestone 2.1 — Database Schema and Migrations

Status: Complete
Parent: 2
Depends on: 1.3
Owner: Repository maintainer

## Goal

Create a versioned PostgreSQL schema and async database access layer for transaction storage and processing state.

## Why this matters

Migration-driven schema changes are reproducible, reviewable, and safe to run in local and future AWS environments. The schema also defines the idempotency and audit invariants that protect asynchronous processing.

## Scope

- SQLAlchemy 2 async engine and session factory
- asyncpg driver
- Alembic configuration
- `transactions`, `risk_assessments`, and `processing_events` tables
- UTC and numeric amount constraints

## Out of scope

- `outbox_events`; it belongs to 3.1.
- Redis state
- API routes
- AWS RDS

## Expected changes

Add database models, repository/session modules, Alembic environment, initial migration, and configuration validation.

## Implementation checklist

- [x] Add async engine and session factory.
- [x] Define `transactions` with unique `transaction_id`.
- [x] Define `risk_assessments` with one current result per transaction.
- [x] Define `processing_events` for attempt/audit history.
- [x] Generate and review initial Alembic migration.
- [x] Add migration upgrade/downgrade validation.

## Interfaces and contracts

`amount` is `NUMERIC(18, 2)`. Event and created timestamps are timezone-aware UTC values. `transaction_id` is a stable external identifier and is unique. Risk status values are `pending`, `processing`, `completed`, and `failed`.

## Validation

```bash
alembic upgrade head
alembic downgrade base
alembic upgrade head
```

Run offline SQL generation locally and against a disposable PostgreSQL instance
in integration tests.

## Acceptance criteria

- [x] Schema is created only through Alembic migrations.
- [x] Duplicate transaction IDs are rejected by PostgreSQL constraints.
- [x] Amount precision and UTC timestamp behavior are covered by contract tests.
- [x] Foreign keys and indexes support transaction/risk lookup.
- [x] Migration is repeatable on a clean PostgreSQL database.

## Failure and edge cases

An invalid `DATABASE_URL`, unavailable database, failed migration, or timezone-naive timestamp must fail explicitly. Application startup must not silently create an incompatible schema.

## Definition of done

The initial migration runs on a clean PostgreSQL container, repositories can open/commit/rollback async sessions, and schema invariants are covered by tests.

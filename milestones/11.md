# Milestone 11 — GitHub Actions and Repository Controls

Status: Not started
Parent: —
Depends on: 1.3, 10
Owner: Repository maintainer

## Goal

Turn the documented quality and security expectations into reliable pull request gates without requiring AWS access.

## Why this matters

CI is the executable form of repository policy. It prevents broken contracts from merging and keeps local-first development independent from cloud credentials and costs.

## Scope

- Python quality checks
- Terraform validation
- Docker build checks
- Integration test execution
- Dependency/security feature boundary
- Branch protection and environment controls

## Out of scope

- Automatic AWS apply
- Production release automation
- Long-running load testing

## Expected changes

Child milestones 11.1 and 11.2 define CI jobs and GitHub repository settings.

## Implementation checklist

- [ ] Complete 11.1.
- [ ] Complete 11.2.
- [ ] Configure required checks only after job names are stable.

## Interfaces and contracts

PRs must pass Python quality, relevant Terraform validation, tests, and Docker build checks. AWS plan/apply/destroy remains manual and environment-protected.

## Validation

Open a test PR containing a deliberate lint, test, Terraform, and dependency change; verify each gate reacts correctly.

## Acceptance criteria

- [ ] CI is reproducible without AWS credentials.
- [ ] Required checks block merges when they fail.
- [ ] Security checks do not claim support when GitHub does not provide it.

## Failure and edge cases

Fork PRs must not receive write permissions or production secrets. A missing Terraform root or Dockerfile must be skipped explicitly rather than creating a false failure.

## Definition of done

Pull requests cannot merge around the project’s quality and security boundaries.

## Follow-up

Use OIDC and required environments when AWS access becomes available in 12.4.

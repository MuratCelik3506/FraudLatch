# Milestone 5.3 — Amount Deviation Context

Status: Not started
Parent: 5
Depends on: 5.1
Owner: Repository maintainer

## Goal

Restore the proposal’s `AMOUNT_DEVIATION` rule using a deterministic customer baseline without exposing fraud labels to the live scorer.

## Why this matters

A transaction that differs sharply from a customer’s normal amount pattern is a useful explainable signal. Implementing it as a separate context provider keeps rules-v1 aligned with the proposal while preserving the pure-engine boundary.

## Scope

- Customer amount baseline
- Deterministic mean/dispersion or configured percentile representation
- `AMOUNT_DEVIATION` reason code
- Cold-start behavior
- Offline baseline preparation
- Label-isolation tests

## Out of scope

- Online model training
- Runtime access to fraud labels
- Long-term feature store
- Customer-level metric labels

## Expected changes

Add a deterministic baseline builder, amount-deviation context object, rules-v1 integration, and fixtures derived from canonical source fields only.

## Implementation checklist

- [ ] Define the baseline window/source partition.
- [ ] Build customer baselines without using `fraud` labels as features.
- [ ] Define a deterministic cold-start result.
- [ ] Calculate deviation using the same event-time contract as replay.
- [ ] Emit `AMOUNT_DEVIATION` when the configured threshold is exceeded.
- [ ] Add boundary and label-leakage tests.
- [ ] Persist the rule reason with the risk result.

## Interfaces and contracts

The provider returns baseline context; `assess(transaction, context)` remains pure. A customer without sufficient history receives a documented neutral context.

## Validation

Test normal amounts, high deviations, insufficient history, equal amounts, timestamp ordering, and repeated deterministic builds.

## Acceptance criteria

- [ ] Proposal Rule 5 is represented in rules-v1.
- [ ] Baseline generation is deterministic.
- [ ] Fraud labels are not read by the live scoring path.
- [ ] Cold-start scoring is safe and documented.
- [ ] Reason code and engine version are persisted.

## Failure and edge cases

Missing baseline, zero variance, invalid amount, future event time, and corrupted baseline files must produce a defined neutral/error path rather than division-by-zero or arbitrary risk.

## Definition of done

Amount deviation works as an explainable, deterministic rules-v1 signal and has no label leakage.

## Follow-up

Include this rule in worker integration and offline evaluation.

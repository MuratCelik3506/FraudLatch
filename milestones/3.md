# Milestone 3 — Transactional Outbox

Status: Not started
Parent: —
Depends on: 2.2, 4.2
Owner: Repository maintainer

## Goal

Make transaction persistence and event creation atomic, then deliver pending events through an isolated dispatcher.

## Why this matters

Directly writing to PostgreSQL and publishing to a queue creates a dual-write window. The outbox makes the database the durable hand-off point and allows delivery to recover after queue or process failures.

## Scope

- Outbox schema and atomic transaction write
- Dedicated dispatcher process
- Publish retry and state tracking
- Duplicate publish tolerance

## Out of scope

- Risk worker behavior
- AWS SQS
- Business-level rule evaluation

## Expected changes

Child milestones 3.1 and 3.2 define the outbox table, API transaction boundary, dispatcher loop, and metrics.

## Implementation checklist

- [ ] Complete 3.1.
- [ ] Complete 3.2.
- [ ] Verify queue outage recovery without losing accepted transactions.

## Interfaces and contracts

The API writes a transaction and one `transaction.received` outbox event in one database transaction. The dispatcher is the only component that publishes pending outbox rows.

Because the dispatcher publishes through the queue port, the Redis Streams adapter in 4.2 must be implemented before 3.2 is considered complete.

## Validation

Use database failure and dispatcher restart tests from 3.1 and 3.2.

## Acceptance criteria

- [ ] Accepted transactions always have a durable event hand-off.
- [ ] Dispatcher retries without deleting failed rows.
- [ ] Duplicate publication is safe for the worker.

## Failure and edge cases

A dispatcher crash after publish and before marking the row published is expected to produce a duplicate; downstream idempotency must handle it.

## Definition of done

Both child milestones pass and a queue outage does not cause accepted transactions to disappear.

## Follow-up

Connect the dispatcher to the Redis Streams adapter in 4.2.

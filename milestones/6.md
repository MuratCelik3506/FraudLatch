# Milestone 6 — Worker Processing

Status: Complete
Parent: —
Depends on: 3.2, 4.3, 5
Owner: Repository maintainer

## Goal

Consume transaction events, calculate risk asynchronously, persist results, and handle duplicates and failures safely.

## Why this matters

The worker is the project’s distributed-systems core. Its acknowledgement boundary, idempotency behavior, and failure policy determine whether the platform can claim reliable processing.

## Scope

- Consumer lifecycle
- Event validation and lookup
- Velocity context and risk engine integration
- Risk result persistence
- Acknowledge-after-commit behavior
- Retry/DLQ integration

## Out of scope

- HTTP ingestion behavior
- AWS ECS deployment
- ML scoring

## Expected changes

Child milestones 6.1 and 6.2 define the worker loop and result/audit persistence.

## Implementation checklist

- [x] Complete 6.1.
- [x] Complete 6.2.
- [ ] Run duplicate, crash, retry, and DLQ scenarios.

## Interfaces and contracts

The worker consumes `EventEnvelope[TransactionReceived]` and produces a persisted `RiskAssessment`. Queue acknowledgement occurs only after a successful database commit.

## Validation

Use Redis and PostgreSQL integration tests plus a full submit-to-result smoke test.

## Acceptance criteria

- [ ] Accepted events eventually produce a risk state.
- [ ] Duplicate delivery does not duplicate results.
- [ ] Failed dependencies trigger the bounded retry policy.
- [ ] Permanent failures reach DLQ.

## Failure and edge cases

Worker crash, database commit failure, Redis outage, malformed event, unknown transaction, and graceful shutdown must have explicit behavior.

## Definition of done

The local asynchronous pipeline is reliable under normal, duplicate, and failure processing.

## Follow-up

Connect replay and observability after the worker passes its integration tests.

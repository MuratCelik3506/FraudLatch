# Milestone 8 — Observability

Status: Not started
Parent: —
Depends on: 2, 3, 6
Owner: Repository maintainer

## Goal

Make ingestion, outbox delivery, queue processing, risk decisions, retries, and DLQ state measurable and diagnosable.

## Why this matters

A distributed system cannot be validated from final database rows alone. Metrics, structured logs, health endpoints, and dashboards make failures visible and support the project’s operational story.

## Scope

- Application metrics
- Structured logs
- Health/readiness
- Prometheus scraping
- Grafana provisioning

## Out of scope

- Distributed tracing
- OpenTelemetry
- CloudWatch implementation

## Expected changes

Child milestones 8.1 and 8.2 define instrumentation and local monitoring resources.

## Implementation checklist

- [ ] Complete 8.1.
- [ ] Complete 8.2.
- [ ] Verify dashboard values during replay and failure tests.

## Interfaces and contracts

Metrics must use the `fraudlatch_` prefix and avoid transaction/customer IDs as labels. Logs must be structured and correlation-friendly.

## Validation

Run a replay, induce a worker failure, and confirm metrics/logs explain received, processed, retried, and dead-lettered messages.

## Acceptance criteria

- [ ] Operational backlog and failure signals are visible.
- [ ] Health and readiness have distinct semantics.
- [ ] Dashboard can be provisioned from a clean local environment.

## Failure and edge cases

Monitoring failure must not silently mark application work successful. Metrics emission must not block or crash transaction processing.

## Definition of done

A maintainer can identify throughput, latency, failures, outbox backlog, and DLQ growth without inspecting raw database rows.

## Follow-up

Use observability outputs in 10.3 failure acceptance tests.

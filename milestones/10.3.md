# Milestone 10.3 — Failure and End-to-End Tests

Status: Complete
Parent: 10
Depends on: 7–10.2
Owner: Repository maintainer

## Goal

Verify the complete local flow and prove that expected failures do not cause silent data loss or duplicate risk results.

## Why this matters

Failure handling is a primary project outcome. A green happy-path test alone cannot demonstrate at-least-once processing, bounded retries, or DLQ behavior.

## Scope

- Submit → outbox → dispatcher → Redis → worker → query
- Duplicate transaction/event
- PostgreSQL restart
- Redis restart
- Worker crash
- Poison message
- Retry exhaustion and DLQ

## Out of scope

- AWS smoke test
- Production traffic volume
- Chaos engineering framework

## Expected changes

Add E2E fixtures, controlled dependency failure helpers, DLQ assertions, and local smoke script integration.

## Implementation checklist

- [x] Replay at least 1,000 canonical transactions.
- [x] Query completed and pending risk states.
- [x] Submit same transaction repeatedly.
- [x] Stop/restart worker with pending work.
- [x] Restart PostgreSQL and verify retry.
- [x] Inject a poison event and verify DLQ.
- [x] Verify no duplicate assessment rows.

## Interfaces and contracts

The test observes only public API results, durable database state, queue/DLQ contracts, and documented metrics/logs.

## Validation

Run the full local stack from clean Terraform state and execute the smoke test; capture counts, failures, and DLQ results.

## Acceptance criteria

- [ ] A normal event reaches a completed risk result.
- [ ] Duplicate delivery produces one current result.
- [ ] Worker crash causes reprocessing without data loss.
- [ ] Three failures move a poison message to DLQ.
- [ ] Database outage is retried and visible.
- [ ] Replay labels are used only in offline evaluation.

## Failure and edge cases

Test interruption between publish and outbox update, interruption between DB commit and ack, empty queue, and zero-result dashboard ranges.

## Definition of done

The local platform demonstrates its reliability claims through repeatable automated scenarios.

## Follow-up

Make the relevant tests required in CI through 11.1.

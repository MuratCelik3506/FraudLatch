# Milestone 2.2 — Transaction Ingestion API

Status: Not started
Parent: 2
Depends on: 2.1
Owner: Repository maintainer

## Goal

Expose a validated API for accepting and querying canonical transactions without coupling ingestion to risk processing.

## Why this matters

Separating acceptance from scoring gives clients a predictable low-latency response and gives the worker pipeline room for retries, scaling, and failure handling.

## Scope

- `POST /v1/transactions`
- `GET /v1/transactions/{transaction_id}`
- `GET /v1/transactions/{transaction_id}/risk` (implemented with result persistence in 6.2)
- `GET /v1/risks/high` (implemented with result persistence in 6.2)
- `GET /health`
- `GET /ready`
- Pydantic request/response models
- Async repository operations
- Same-payload idempotency and conflicting-payload detection

## Out of scope

- Risk calculation
- Queue publish; 3.1 adds the outbox write.
- Authentication
- Ground-truth labels in external requests

## Expected changes

Add FastAPI application factory, route modules, dependency providers, transaction service, and API tests.

## Implementation checklist

- [ ] Define `TransactionIn` without fraud-label fields.
- [ ] Validate positive amount, required IDs, category, and timezone-aware event time.
- [ ] Implement insert-and-compare duplicate behavior.
- [ ] Return `202` for accepted and already-accepted transactions.
- [ ] Return `409` for same ID with different canonical payload.
- [ ] Implement liveness and readiness separately.
- [ ] Add OpenAPI contract tests.

## Interfaces and contracts

```text
POST /v1/transactions       -> 202 accepted/already_accepted
GET  /v1/transactions/{id}  -> 200 transaction or 404
GET  /health                -> 200 without checking dependencies
GET  /ready                 -> 200 only when PostgreSQL and Redis are ready
```

The API does not wait for a risk result and never accepts `is_fraud` as a scoring input.

## Validation

Use FastAPI/HTTPX tests for valid, invalid, duplicate, conflict, missing, and dependency-failure cases.

## Acceptance criteria

- [ ] Valid input is persisted and returns `202`.
- [ ] Identical retries do not create a second transaction.
- [ ] Conflicting retries return `409`.
- [ ] Invalid input returns `422` with field-level details.
- [ ] Risk is not calculated in the request lifecycle.

## Failure and edge cases

Concurrent identical requests must be safe under the database unique constraint. A failed commit must not return an accepted response. Internal database errors must not expose SQL or stack traces.

## Definition of done

API contract tests pass against the migration-created schema and a client can submit and query a transaction without a queue or worker.

## Follow-up

Add an atomic `outbox_events` insert to this service in 3.1.

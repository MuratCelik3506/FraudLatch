# Milestone 13.1 — Offline ML Baseline

Status: Deferred
Parent: 13
Depends on: 7, 10
Owner: Repository maintainer

## Goal

Compare a simple offline ML baseline with rules-v1 without changing the live processing contract.

## Why this matters

The proposal treats ML as a benchmark, not the project’s primary showcase. Keeping it offline avoids online retraining and deployment complexity.

## Scope

- Logistic Regression or Gradient Boosting baseline
- Reproducible train/evaluation split
- Precision, recall, F1, PR-AUC, and fraud recall
- Rules-v1 versus ml-v1 report

## Out of scope

- Online model serving
- Retraining in the worker
- Label use in live scoring

## Expected changes

Add an offline evaluation script/notebook and versioned model metadata; do not change the API risk engine by default.

## Implementation checklist

- [ ] Define time-based train/evaluation split.
- [ ] Exclude labels from live feature payloads.
- [ ] Record seed, features, library versions, and metrics.
- [ ] Compare rules-v1 and ml-v1 on the same evaluation rows.
- [ ] Document class imbalance and threshold trade-offs.

## Interfaces and contracts

ML output is an offline report; `rules-v1` remains the production/default engine until a separate deployment decision is approved.

## Validation

Repeat the evaluation with the same seed and verify identical metrics and split membership.

## Acceptance criteria

- [ ] Metrics include PR-AUC, precision, recall, F1, and fraud recall.
- [ ] Evaluation has no train/evaluation leakage.
- [ ] Live worker behavior is unchanged.

## Failure and edge cases

Missing labels, severe class imbalance, and feature leakage must fail or be reported explicitly.

## Definition of done

An auditable offline comparison exists without changing the core architecture.

## Follow-up

Consider model serving only in a separate ADR.

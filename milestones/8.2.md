# Milestone 8.2 — Prometheus and Grafana

Status: Complete
Parent: 8
Depends on: 8.1, 9.3
Owner: Repository maintainer

## Goal

Provide a reproducible local monitoring stack with a preconfigured Prometheus datasource and Grafana dashboard.

## Why this matters

A dashboard makes the event-driven behavior and failure handling demonstrable. Provisioning avoids a manual setup step that cannot be reproduced by another contributor.

## Scope

- Prometheus scrape configuration
- Grafana datasource provisioning
- Dashboard JSON
- API/worker targets
- Throughput, latency, risk, failure, backlog, and DLQ panels

## Out of scope

- CloudWatch dashboards
- Alert routing integrations
- Distributed tracing

## Expected changes

Add monitoring configuration under `monitoring/` and Terraform mounts under the local infrastructure root.

## Implementation checklist

- [x] Configure scrape targets for API and worker.
- [x] Provision Prometheus datasource automatically.
- [x] Create dashboard JSON with stable metric queries.
- [x] Add dashboard documentation and local URLs.
- [x] Verify dashboard after replay and injected failure.

## Interfaces and contracts

Dashboard queries must use metric names from 8.1 and remain valid if no data exists yet.

## Validation

Start the monitoring stack from clean state and verify scrape health, datasource status, and panel data.

## Acceptance criteria

- [ ] No manual dashboard import is required.
- [ ] API and worker metrics are distinguishable.
- [ ] Outbox backlog and DLQ count are visible.
- [ ] Dashboard remains usable with zero traffic.

## Failure and edge cases

Prometheus target down and empty metric ranges must show a meaningful state, not a misleading zero-success claim.

## Definition of done

Terraform can start monitoring and a maintainer can inspect the complete local pipeline from Grafana.

## Follow-up

Use dashboard screenshots and queries in README after local E2E completion.

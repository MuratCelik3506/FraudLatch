# Milestone 13.5 — OpenTelemetry Tracing

Status: Deferred
Parent: 13
Depends on: 8, 12.4
Owner: Repository maintainer

## Goal

Trace an event across API, outbox dispatcher, queue, worker, database, and risk engine boundaries.

## Why this matters

Metrics show aggregate health; traces explain an individual slow or failed path. This is useful only after stable logs, metrics, and cloud deployment exist.

## Scope

- OpenTelemetry SDK
- Trace/span propagation through event envelope metadata
- API and worker spans
- Exporter configuration
- Sampling policy

## Out of scope

- Storing sensitive payloads in spans
- Mandatory tracing for local MVP
- Vendor-specific production lock-in

## Expected changes

Add tracing helpers, propagation fields, exporter configuration, and a troubleshooting guide.

## Implementation checklist

- [ ] Define trace/correlation propagation policy.
- [ ] Instrument API, dispatcher, Redis/SQS adapter, worker, and database calls.
- [ ] Redact transaction payload and sensitive values.
- [ ] Configure local and AWS exporters separately.
- [ ] Add sampling and cost limits.

## Interfaces and contracts

Tracing is additive and must not change event business semantics or processing outcomes.

## Validation

Submit one transaction and verify one coherent trace across all available components.

## Acceptance criteria

- [ ] A transaction can be followed across service boundaries.
- [ ] Sensitive payload values are absent from spans.
- [ ] Exporter failure does not fail processing.

## Failure and edge cases

Missing exporter, propagation loss, clock skew, and high-volume span cost must be visible and bounded.

## Definition of done

Distributed traces improve diagnosis without becoming a runtime dependency.

## Follow-up

Review tracing cost and sampling before enabling it in any persistent AWS environment.

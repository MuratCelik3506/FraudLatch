# Milestone 10.1 — Unit and Contract Tests

Status: Complete
Parent: 10
Depends on: 2–7
Owner: Repository maintainer

## Goal

Cover pure contracts and deterministic logic without requiring PostgreSQL, Redis, Docker, or AWS.

## Why this matters

Fast unit tests provide immediate feedback and isolate regressions in validation, event schemas, risk rules, replay determinism, and failure classification.

## Scope

- Pydantic validation
- Event envelope serialization
- Deterministic IDs/timestamps
- Rules engine
- Idempotency semantics
- Retry classification

## Out of scope

- Real database operations
- Real Redis Streams
- Process restart tests

## Expected changes

Add unit tests under `tests/unit` and queue/risk/data contract fixtures.

## Implementation checklist

- [x] Test valid/invalid transaction requests.
- [x] Test duplicate same-payload and conflicting-payload rules.
- [x] Test event envelope round trips and versions.
- [x] Test rules boundaries and reason ordering.
- [x] Test timestamp/ID determinism.
- [x] Test transient/permanent error classification.
- [x] Test fraud-label exclusion from scoring input.

## Interfaces and contracts

Unit tests must call pure functions or fakes implementing the documented ports; they must not import concrete Redis/PostgreSQL clients.

## Validation

```bash
pytest -m 'not integration'
```

## Acceptance criteria

- [ ] All contract boundary cases have tests.
- [ ] Repeated deterministic inputs have identical outputs.
- [ ] No unit test depends on local service state.
- [ ] Failures identify the violated contract clearly.

## Failure and edge cases

Tests must cover timezone-naive timestamps, unsupported schema versions, negative amounts, empty IDs, score boundaries, and unknown reason codes.

## Definition of done

Pure logic and public contracts can be safely refactored with fast feedback.

## Follow-up

Use real service containers in 10.2.

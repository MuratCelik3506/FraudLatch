# Milestone 12.4 — ECS, Persistence, and Deployment

Status: Deferred
Parent: 12
Depends on: 12.1, 12.3
Owner: Repository maintainer

## Goal

Deploy the proven application to AWS ECS/Fargate with managed persistence, messaging, logging, and a safe manual lifecycle.

## Why this matters

This is the final cloud demonstration: the same API/worker contract runs on reproducible infrastructure with explicit costs, health checks, IAM, and destroy behavior.

## Scope

- ECR API/dispatcher/worker repositories
- ECS cluster and task definitions
- API, dispatcher, and worker services
- ALB and target groups
- RDS PostgreSQL
- ElastiCache Redis
- CloudWatch logs and alarms
- Manual OIDC apply/destroy smoke test

## Out of scope

- Kubernetes/EKS
- Blue/green deployment
- Multi-region failover
- Production SLA claims

## Expected changes

Add Terraform modules for compute, persistence, observability, and deployment wiring in `aws-dev`.

## Implementation checklist

- [ ] Build and push immutable API/worker image tags.
- [ ] Configure ECS task health checks and resource limits.
- [ ] Register API target group behind ALB.
- [ ] Run the dispatcher as a private ECS service that publishes pending outbox events to SQS.
- [ ] Run worker privately with SQS access.
- [ ] Configure RDS backups and deletion protection appropriate for dev.
- [ ] Configure ElastiCache connectivity.
- [ ] Send container logs to CloudWatch.
- [ ] Publish CloudWatch metrics for queue depth, task health, error rate, and processing latency.
- [ ] Add queue depth/task health/error/latency alarms.
- [ ] Verify required cost tags and AWS Budget alarm before the demo.
- [ ] Run apply → smoke test → destroy manually.

## Interfaces and contracts

The deployed API exposes the same endpoints and status semantics as local. The worker uses the same `QueuePort`, event envelope, idempotency, retry, and risk result contracts.

## Validation

```text
terraform plan
terraform apply
push images
POST transaction
query risk result
inspect logs/metrics
terraform destroy
```

## Acceptance criteria

- [ ] API is reachable only through the intended ALB path.
- [ ] Dispatcher publishes a pending outbox event to SQS.
- [ ] Worker processes an SQS event and persists a result.
- [ ] CloudWatch logs, metrics, and alarms show service health.
- [ ] Manual destroy removes development resources.
- [ ] No long-lived AWS credentials are used by GitHub Actions.

## Failure and edge cases

Unhealthy task, failed deployment, inaccessible secret, database migration failure, queue backlog, and destroy failure must have runbook instructions and clear alarm/log evidence.

## Definition of done

FraudLatch runs end-to-end in AWS dev and can be fully removed after a demonstration.

## Follow-up

Only after this milestone may autoscaling, blue/green deployment, tracing, or ML comparison be considered as separate milestones.
